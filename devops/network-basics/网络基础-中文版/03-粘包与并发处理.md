# 3. 粘包与并发处理

本章处理两个进阶主题：TCP 字节流导致的消息边界问题（粘包），以及单线程服务多个客户端的并发方案（非阻塞 socket 与 IO 多路复用）。

## 3.1 TCP 粘包问题及解决方案

TCP 是**面向字节流（stream-oriented）** 的协议。与 UDP 中每次 `send` 对应一个数据报不同，TCP 将数据视为连续的字节流。操作系统使用**发送缓冲区和接收缓冲区**来管理这个字节流，这可能导致**粘包（sticky packet）** 问题。

### 3.1.1 粘包是如何产生的

当客户端连续快速发送多个小消息时，TCP 可能会在发送前将它们合并为单个流段。在接收端，`recv(n)` 只是从接收缓冲区中读取最多 `n` 个字节，而不管发送方一共发送了多少条逻辑消息。

**示例：**

```python
# 客户端分别发送三条消息
client.send("abc".encode())
client.send("123".encode())
client.send("456".encode())
```

在服务器端，`recv(1024)` 可能会把它们作为一整块一次性接收：

```
b'abc123456'
```

这使得接收方无法知道一条消息在哪里结束、下一条消息从哪里开始。

**原因：**
- **发送方**：操作系统可能会合并小消息以提高效率（Nagle 算法）。
- **接收方**：如果接收方比发送方慢，接收缓冲区中可能会堆积多条消息。

### 3.1.2 演示这个问题

完整可运行示例：[TCP 粘包演示 — 服务器](../examples/zh/tcp_server_sticky_demo.py) · [客户端](../examples/zh/tcp_client_sticky_demo.py)

```python
# server.py
import socket

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server.bind(('127.0.0.1', 9090))
server.listen(5)
conn, addr = server.accept()

# 循环读取，观察粘包现象
while True:
    info = conn.recv(10)
    if not info:
        break
    print(f"Received ({len(info)} bytes): {info.decode()}")

conn.close()
server.close()
```

```python
# client.py
import socket

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect(('127.0.0.1', 9090))

# 快速连续发送多条小消息，增加粘包概率
for i in range(10):
    client.send(f"msg-{i}".encode())

client.close()
```

![[tcp-sticky-packet-demo.png]]

> 实际运行效果：客户端连续发送 `msg-0` 到 `msg-9` 共 10 条消息（每条 5 字节），但服务器的 `recv(10)` 多次把两条消息合并成一次读取（如 `msg-1msg-2`）——消息边界完全丢失，这就是粘包。

### 3.1.3 权宜之计：发送之间加延时

在两次发送之间添加 `time.sleep(1)` 可以缓解这个问题，因为操作系统可能会在下一条消息写入之前先把第一个包发出去。但是这种方法**不可靠**，而且会严重损害性能。

```python
import time

client.send("abc".encode())
time.sleep(1)
client.send("123".encode())
time.sleep(1)
client.send("456".encode())
```

> ⚠️ **不要**在生产环境中使用这种方法。它只是一个快速演示用的临时修复。

### 3.1.4 正确的解决方案：长度前缀头部

标准的解决方案是先发送一个**固定长度的头部（header）**，其中包含紧随其后的消息的大小。接收方先读取头部，然后精确地读取指定数量的字节。

**设计：**
1. 将消息长度作为 4 字节整数头部发送。
2. 发送实际的消息数据。
3. 接收方读取 4 字节，解包得到长度，然后精确读取该数量的字节。

在 Python 中，使用 `struct` 模块在整数与 4 字节二进制格式之间进行转换：

```python
import struct

# 按网络字节序将整数打包为 4 个字节
length_bytes = struct.pack("!I", 100)  # 4 个字节
print(len(length_bytes))  # 4

# 解包还原为整数
length_tuple = struct.unpack("!I", length_bytes)
print(length_tuple)      # (100,)
print(length_tuple[0])   # 100
```

> **格式 `"!I"`**：网络字节序的无符号 4 字节整数。它使头部长度固定且跨平台一致；实际应用仍应设置最大消息长度。

### 3.1.5 长度前缀协议的完整实现

把长度前缀协议直接封装成 `util.py` 中三个可复用的辅助函数。其中关键是 `recv_exactly`：`recv(n)` 一次可能读不满 `n` 个字节，必须循环读取直到读满（对方断开时返回 `None`）。`recv_with_length` 就是前面三步流程的封装：读 4 字节头部 → 解包得到长度 → 精确读取正文，并加上最大消息长度保护。

完整可运行示例：[util.py](../examples/zh/util.py) · [服务器](../examples/zh/length_prefix_server.py) · [客户端](../examples/zh/length_prefix_client.py)

```python
# util.py
import struct

HEADER_FORMAT = '!I'
HEADER_SIZE = struct.calcsize(HEADER_FORMAT)
MAX_MESSAGE_SIZE = 16 * 1024 * 1024


def recv_exactly(sock, size):
    """循环读取，直到读满 size 个字节；对方断开连接时返回 None。"""
    chunks = bytearray()
    while len(chunks) < size:
        chunk = sock.recv(size - len(chunks))
        if not chunk:
            return None
        chunks.extend(chunk)
    return bytes(chunks)


def send_with_length(sock, message):
    """使用 4 字节长度头部发送字符串消息。"""
    data = message.encode()
    length = len(data)
    if length > MAX_MESSAGE_SIZE:
        raise ValueError('message is too large')
    sock.sendall(struct.pack(HEADER_FORMAT, length))
    sock.sendall(data)


def recv_with_length(sock):
    """使用 4 字节长度头部接收字符串消息。

    返回解码后的消息；如果对方断开连接，则返回 None。
    """
    header = recv_exactly(sock, HEADER_SIZE)
    if header is None:
        return None

    length = struct.unpack(HEADER_FORMAT, header)[0]
    if length > MAX_MESSAGE_SIZE:
        raise ValueError('message is too large')
    data = recv_exactly(sock, length)
    if data is None:
        return None

    return data.decode()
```

服务器和客户端都直接使用这两个辅助函数：

```python
# length_prefix_server.py
import socket
from util import send_with_length, recv_with_length

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.bind(('127.0.0.1', 9090))
server.listen(5)
conn, addr = server.accept()

while True:
    msg = recv_with_length(conn)
    if msg is None:
        print("Client disconnected unexpectedly")
        break
    if msg == 'exit':
        print("Client exited")
        break

    print(f"From client: {msg}")
    send_with_length(conn, "Hello from server")

conn.close()
server.close()
```

```python
# length_prefix_client.py
import socket
from util import send_with_length, recv_with_length

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect(('127.0.0.1', 9090))

while True:
    info = input("Message: ")
    if info == '':
        print("Cannot send empty message")
        continue

    send_with_length(client, info)

    if info == 'exit':
        break

    reply = recv_with_length(client)
    print(f"Server reply: {reply}")

client.close()
```

### 3.1.6 重要说明

- 接收方不应使用 `recv(1024)` 来接收任意长度的消息。它应当精确读取头部声明的长度，如果数据较大，可能需要循环读取。
- 对于生产系统，可以考虑使用成熟的协议或库（例如 HTTP、JSON-RPC、gRPC、`asyncio` 流、配合网络字节序 `!I` 使用的 `struct`）。
- 长度前缀使用 `!I`，表示网络字节序的无符号 4 字节整数，适合跨平台通信。
- TCP 示例使用 `sendall()` 确保数据完整发送；如果使用 `send()`，必须循环检查返回的字节数。

## 3.2 非阻塞 Socket

默认情况下，`accept()` 和 `recv()` 等 socket 方法是**阻塞（blocking）** 的：程序会一直暂停，直到有客户端连接或有数据到达。对于单个客户端这没有问题，但它会使单个线程无法同时处理多个客户端。

### 3.2.1 什么是非阻塞？

**非阻塞 socket（non-blocking socket）** 在没有数据或连接可用时会立即返回，抛出 `BlockingIOError` 异常而不是等待。这样，一个线程就可以在循环中轮询多个 socket。

```python
server.setblocking(False)  # 将 socket 设为非阻塞
```

### 3.2.2 用非阻塞 Socket 处理多个客户端

服务器维护一个已连接客户端 socket 的列表。在每次循环迭代中：

1. 尝试 `accept()` 一个新连接。如果没有，捕获异常并继续。
2. 遍历所有已有连接，尝试从每个连接 `recv()`。
3. 将已断开连接的客户端从列表中移除。

```python
# server.py
import socket

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.bind(('127.0.0.1', 9090))
server.listen(5)
server.setblocking(False)

connections = []

while True:
    # 尝试接受新连接
    try:
        conn, addr = server.accept()
        conn.setblocking(False)
        connections.append(conn)
        print(f"New connection from {addr}")
    except BlockingIOError:
        pass

    # 检查每个连接是否有传入数据
    disconnected = []
    for conn in connections:
        try:
            msg = conn.recv(1024)
            if not msg:
                # 客户端正常关闭连接
                disconnected.append(conn)
                continue

            text = msg.decode()
            if text == 'exit':
                disconnected.append(conn)
                continue

            print(f"Received: {text}")
            conn.send("Hello from server".encode())
        except BlockingIOError:
            # 当前客户端暂时没有可用数据
            pass
        except ConnectionResetError:
            disconnected.append(conn)

    # 移除已断开的客户端
    for conn in disconnected:
        if conn in connections:
            connections.remove(conn)
        conn.close()
```

```python
# client.py
import socket

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect(('127.0.0.1', 9090))

while True:
    info = input("Message: ")
    if info == '':
        print("Cannot send empty message")
        continue

    client.send(info.encode())
    if info == 'exit':
        break

    msg = client.recv(1024)
    print(f"Server reply: {msg.decode()}")

client.close()
```

> **注意**：不要在遍历 `connections` 的循环里直接 `remove` 元素——遍历中删除会打乱索引，导致跳过元素、漏掉检查。上面的代码先把要断开的连接收集到 `disconnected` 列表，等遍历结束后再统一删除。

### 3.2.3 非阻塞 Socket 的优缺点

| 优点 | 缺点 |
|------|------|
| 一个线程可以管理多个连接 | 由于不断轮询，CPU 占用率高 |
| 概念上容易理解 | 大量 `try/except` 代码块使代码杂乱 |
| 不需要多线程或多进程 | 当大多数连接处于空闲状态时效率低下 |

对于正式的服务器，通常更倾向于使用 3.3 介绍的 IO 多路复用，而不是纯粹的非阻塞轮询。

## 3.3 使用 `select` 实现 IO 多路复用

**IO 多路复用（IO multiplexing）** 让操作系统同时监控多个 socket，并且只在其中某个 socket 可以读写时才通知程序。它比在循环中轮询每个 socket 更高效。

在 Python 中，`select` 模块提供了这一能力。核心函数是：

```python
readable, writable, exceptional = select.select(rlist, wlist, xlist)
```

| 参数 | 含义 |
|-----------|---------|
| `rlist` | 需要监控是否有传入数据的 socket（可读就绪） |
| `wlist` | 需要监控是否可以发送数据的 socket（可写就绪） |
| `xlist` | 需要监控异常情况的 socket（通常为空） |

该函数会**阻塞**，直到至少有一个 socket 就绪，然后返回三个就绪 socket 的列表。

### 3.3.1 基本工作流程

1. 将服务器 socket 放入 `rlist`。
2. 当 `select` 返回时，检查每个就绪的 socket：
   - 如果就绪的 socket 是**服务器 socket**，调用 `accept()` 并将新连接加入 `rlist`。
   - 如果就绪的 socket 是**客户端连接**，调用 `recv()` 读取数据。
3. 将已关闭的连接从 `rlist` 中移除。

### 3.3.2 使用 `select` 的服务器

```python
import socket
import select

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.bind(('127.0.0.1', 9090))
server.listen(5)
server.setblocking(False)

# 首先监控服务器 socket 的新连接
read_list = [server]

while True:
    readable, _, _ = select.select(read_list, [], [])

    for sock in readable:
        if sock is server:
            # 新的客户端连接
            conn, addr = server.accept()
            conn.setblocking(False)
            read_list.append(conn)
            print(f"New connection from {addr}")
        else:
            # 已连接的客户端发送了数据
            try:
                msg = sock.recv(1024)
                if not msg:
                    # 客户端断开连接
                    print("Client disconnected")
                    read_list.remove(sock)
                    sock.close()
                    continue

                text = msg.decode()
                if text == 'exit':
                    print("Client exited")
                    read_list.remove(sock)
                    sock.close()
                    continue

                print(f"From client: {text}")
                sock.send("Hello from server".encode())
            except ConnectionResetError:
                read_list.remove(sock)
                sock.close()
```

```python
# client.py（与前面相同）
import socket

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect(('127.0.0.1', 9090))

while True:
    info = input("Message: ")
    if info == '':
        print("Cannot send empty message")
        continue

    client.send(info.encode())
    if info == 'exit':
        break

    msg = client.recv(1024)
    print(f"Server reply: {msg.decode()}")

client.close()
```

### 3.3.3 `select` 的优点

| 特性 | 好处 |
|---------|---------|
| 单线程并发 | 无需多线程即可处理多个客户端 |
| 事件驱动 | 只处理就绪的 socket |
| CPU 占用更低 | 不做忙轮询；阻塞直到有事件发生 |
| 可移植 | `select` 在 Unix、Linux、macOS 和 Windows 上均可用 |

### 3.3.4 局限性与替代方案

| 局限性 | 说明 |
|------------|-------------|
| 可扩展性 | `select` 可监控的文件描述符数量有限（Linux 上通常为 1024） |
| 性能 | 对于数千个连接，`poll` 或 `epoll`（Linux）/ `kqueue`（BSD/macOS）性能更好 |
| 现代 Python | 对于高层并发，推荐使用带 `async`/`await` 的 `asyncio` |

### 3.3.5 常见使用场景

- 单线程处理多个连接的聊天服务器
- 简单的 TCP 代理或中继服务
- 需要等待多个数据来源的监控工具
- 在转向 `asyncio` 或 `selectors` 之前学习基础知识

> **小结**：非阻塞 socket + `select` 是构建单线程并发网络服务器的经典方式。对于现代 Python 项目，`asyncio` 建立在相同的思想之上，但提供了更简洁、更高级的 API。

## 3.4 TCP 进阶话题

第 1 章介绍了 TCP 的可靠性机制（1.3.3）和连接管理（1.3.5）。本节补充几个工程实践中会实际遇到的 TCP 话题。

### 3.4.1 流量控制与拥塞控制

TCP 有两个独立的"限速"机制，容易混淆：

| 机制 | 解决什么问题 | 实现方式 |
|------|--------------|----------|
| **流量控制** | 接收方处理不过来 | 接收方通过 **滑动窗口** 告知自己还能接收多少字节，发送方不得超出 |
| **拥塞控制** | 网络链路承受不住 | 发送方维护 **拥塞窗口**，从慢启动开始试探，丢包就减速（如 Reno、CUBIC 算法） |

简单说：1.3.3 讲的是 TCP 如何"传得对"，这里讲的是 TCP 如何"传得不撑死对方、不堵死网络"。实际发送速率取两个窗口的较小值。

### 3.4.2 Nagle 算法与 `TCP_NODELAY`

3.1.1 提到粘包的一个成因是 **Nagle 算法**：它把小包攒起来一起发，以减少网络上的小包数量。这对吞吐量友好，但对延迟不友好。

实时性敏感的应用（游戏、远程终端、即时通信）通常会关掉它：

```python
conn.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
```

代价是失去了合并小包的优化——粘包的概率反而更高，所以关掉 Nagle 的同时更应该使用长度前缀协议（3.1）。

### 3.4.3 `TIME_WAIT` 与 `SO_REUSEADDR`

主动关闭连接的一端会进入 **TIME_WAIT** 状态，端口被占用约 1～4 分钟（等待对方可能重传的最后一个 ACK）。这就是重启服务器时偶尔遇到 `Address already in use` 报错的原因——旧连接还没走完 TIME_WAIT。

本书从第 2 章起所有服务端示例都设置了 `SO_REUSEADDR`，就是为了允许服务器立即重新绑定处于 TIME_WAIT 的端口：

```python
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
```

### 3.4.4 保活与半开连接

如果对端直接断电或断网，没有发送 FIN，本端的连接就成了 **半开连接（half-open）**——`recv` 会一直阻塞，永远等不到通知。

两种应对：

- **TCP 层保活**：`SO_KEEPALIVE` 选项让操作系统定期发送探测包，默认两小时才开始探测，通常太慢。
- **应用层心跳**：自己的协议里定期发一个"我还活着"的小消息（如每 30 秒），连续几次没收到就判定掉线——这是更常见、可控的做法。第 5 章网盘项目要支持"客户端掉线感知"，就应从这里入手。

> **小结**：这四个话题的共同点是——它们都不会出现在"能跑通"的 demo 里，但都会出现在生产事故里。知道它们的存在，排查问题时就有了方向。
